# Конструктор учебных сценариев (Unity / C#)

Система, в которой учебный сценарий собирается и меняется в Unity Editor без программирования:
шаги, порядок и способ их активации, группы, режим прохождения, источники событий, логгер и анализатор
настраиваются ассетами и компонентами в инспекторе. Одни и те же шаги используются во всех режимах.

- **Unity:** 6000.6.4f1 (Built-in Render Pipeline, старый Input Manager, uGUI). Сторонних пакетов нет.
- **Демо:** `Assets/Demo/Scenes/Demo.unity` — сценарий «Запуск насосной станции», 12 шагов, 3 режима.
- **Тесты:** 17 EditMode (ядро, контрольные примеры) + 5 PlayMode (прохождение реальной демо-сцены).

## Быстрый старт

1. Откройте папку проекта в Unity Hub (Add → папка `ScenarioConstructor`) версией 6000.6.x.
2. Откройте сцену `Assets/Demo/Scenes/Demo.unity` и нажмите **Play**.
3. В меню выберите режим: **Тренировка**, **Экзамен** или **Тренировка по шагам**.
4. Управление: **WASD / стрелки** — движение игрока (белая капсула), **мышь** — кнопки пульта справа.
5. Слева — активные задания и сообщения о нарушениях. После завершения откроется результат:
   в выпадающем списке можно выбрать другой анализатор — оценка пересчитается по журналу без повторного прохождения.
   Кнопка **Журнал** показывает все события в любой момент; **Пройти снова** перезапускает режим с чистой сценой.

### Что есть в демо

| Шаг | Что сделать | Источник события |
|---|---|---|
| S01 Проверка связи | кнопка «Проверка связи» | UI Button |
| S02 Включить питание | «Рубильник» (нарушение: «Пуск» до питания) | UnityEvent собственного компонента `PowerSwitch` |
| S03 Осмотр зоны A | зайти в жёлтую зону (нарушение: красная зона) | Trigger |
| S04 Проверка стойки | коснуться серой стойки | Collision |
| S05 Обход B → C | **сначала** синяя зона B, **затем** зелёная C | Trigger, контекстный шаг (порядок) |
| S06 Запуск насоса | «Пуск» **только при включённом питании** | Button + состояние другого объекта |
| S07 Погрузка | затолкать ящик в оранжевую зону | Trigger, реагирует на ящик (тег `Box`) |
| S08 Отчёт | кнопка «Отчёт» | UI Button |
| S09 Выключить питание | «Рубильник» | UnityEvent |
| S10 Возврат на базу | зайти в зону «База» (нарушение: красная зона) | Trigger |
| S11 Подтверждение | «Подтвердить» **только при выключенном питании** | Button + состояние |
| S12 Отметка у терминала | коснуться синего терминала | Collision |

Режимы (все три используют одни и те же 12 ассетов шагов):

- **Тренировка** — одна группа: шаги 1–4 одновременно → 5, 6, 7, 8 по очереди → 9 и 10 вместе → 11 и 12 вместе
  (ровно пример из задания). Нарушение — сообщение и повтор шага. Оценка 10 / 5 / 0 за 1-ю / 2-ю / 3-ю+ попытку.
- **Экзамен** — три группы: «подготовка» (1–4 одновременно), «запуск» (5–8 по очереди), «завершение» (9+10, затем 11+12).
  Нарушение — шаг Failed без повтора; при 2 нарушениях в группе оставшиеся шаги группы Skipped. Итог = max(0, 100 − 10·Failed − 5·Skipped).
- **Тренировка по шагам** — все шаги строго по одному, и шаг до своей очереди **не принимает действия**
  (альтернатива правилу «действие вне очереди = нарушение»).

### Как проверить контрольные примеры вручную

- **Тренировка, 10 / 5 / 0:** нажмите «Проверка связи» (S01 с 1-й попытки → 10); зайдите в красную зону, потом в жёлтую
  (S03 со 2-й → 5); дважды нажмите «Пуск», затем «Рубильник» (S02 с 3-й → 0). В результате по этим трём шагам 15 баллов.
- **Экзамен, 70:** сразу нажмите «Пуск» (S02 Failed) и зайдите в красную зону (S03 Failed) — порог 2 достигнут,
  S01 и S04 становятся Skipped (штраф 20 + 10 = 30). Остальное пройдите без ошибок: B → C, «Рубильник», «Пуск»,
  ящик в погрузку, «Отчёт», «Рубильник», база, «Подтвердить», терминал. Итог — 70.
- **Смешанная активация:** в тренировке шаги 1–4 видны сразу и выполняются в любом порядке; 5–8 появляются по одному;
  9 и 10 — парой после 8; 11 и 12 — после обоих.
- **Действие вне очереди:** в тренировке зайдите в зону B, пока активны шаги 1–4, — это нарушение шага S05.
  В «Тренировке по шагам» то же действие ничего не делает.

Те же сценарии автоматически проверяют тесты (`Window → General → Test Runner`).

## Инструкция для автора сценария (без программирования)

Все ассеты демо лежат в `Assets/Demo/Scenario`. Новые ассеты создаются через **ПКМ в окне Project → Create → Scenario → …**.
Инспекторы сценария, режима и шага сами показывают ошибки настройки (жёлтая плашка сверху) — если плашка синяя, всё в порядке.

### Из чего состоит сценарий

| Ассет | Что это | Где в демо |
|---|---|---|
| **Action Key** | «Название действия»: «нажата кнопка Пуск», «вход в зону A». Связывает объект сцены и шаг. | `Actions/` |
| **State Key** | Логическое состояние мира: «питание включено». | `States/` |
| **Step** (Action Sequence Step) | Шаг: id, название, инструкция, что нужно сделать, условия, запрещённые действия. | `Steps/` |
| **Mode Profile** | Режим: правила, анализатор по умолчанию, группы → этапы → шаги. | `Modes/` |
| **Rules** | Что делать при нарушении: Training (повтор) или Exam (Failed + порог группы). | `Rules/` |
| **Analyzer** | Алгоритм оценки по журналу. | `Analyzers/` |
| **Logger** | Куда писать журнал: консоль Unity, файл JSON Lines. | `Loggers/` |
| **Scenario** | Список шагов и список режимов, которые видны в меню. | `Scenario_PumpStation` |

### Настроить шаг

Выберите ассет шага (например `Steps/S06_StartPump`):

- **Id / Title / Instruction** — идентификатор для журнала, название и текст задания, который видит обучаемый.
- **Sequence** — действия, которые нужно выполнить **по порядку**. Одно действие — простой шаг; два и больше — составной
  («сначала зона B, затем зона C»). **Strict Order** — выполнить действие раньше очереди считается нарушением; если выключить, оно просто игнорируется.
- **Requirements** — условия на состояние других объектов в момент действия: State Key + нужное значение + текст нарушения
  («Пуск только при включённом питании»).
- **Forbidden** — действия, которые считаются нарушением, пока шаг активен (+ текст сообщения).

Внизу инспектора шага видно, в каких режимах он используется — шаги не копируются между режимами.

### Изменить порядок, активацию и группы

Откройте режим (`Modes/Mode_Training` и т.д.). Список **Groups** → у каждой группы список **Stages** → у этапа список **Steps**.
Все списки переупорядочиваются **перетаскиванием за левый край строки**; шаги добавляются кнопкой «+» и перетаскиванием ассета шага.

- **Stage → Activation**: `Simultaneous` — все шаги этапа активны сразу, в любом порядке; `Sequential` — по одному, в порядке списка.
  Следующий этап начинается, когда завершены все шаги текущего. Так собирается любая смешанная схема.
- **Group** — единица правил: порог нарушений и пропуски считаются по группе. Для тренировки достаточно одной группы,
  для экзамена — несколько. **Start**: `After Previous Group` (по умолчанию) или `With Previous Group` (группы идут одновременно, перекрываются).
- Под списком инспектор показывает **«Схему активации»** словами — удобно проверить, что получилось.

### Выбрать режим и правила

- **Rules** в режиме — ассет правил. Порог нарушений экзамена — поле **Violation Threshold** в `Rules/Rules_Exam`.
- **Out Of Turn** — что делать с действием шага, чья очередь ещё не пришла: `Violation` (нарушение этого шага, по умолчанию)
  или `Ignore Until Active` (шаг неактивен и не принимает действия).
- **Default Analyzer** — чем оценивать результат сразу после прохождения.
- Новый режим: Create → Scenario → Mode Profile, заполнить и добавить в список **Modes** ассета сценария — он появится в меню.

### Обработка событий в сцене

Источник действия — компонент на объекте сцены, в котором выбран Action Key (`Add Component → Scenario → Sources`):

- **Button Action Source** — на UI-кнопке; поле **On Click**.
- **Trigger Action Source** — на объекте с коллайдером-триггером; **On Enter / On Exit**, **Actor Tag** (кто должен войти: `Player`, `Box`, пусто — кто угодно).
- **Collision Action Source** — на объекте с коллайдером; **On Collision**, **Actor Tag**, минимальная скорость удара.
- **UnityEvent Action Source** — мост для любого UnityEvent (Toggle, Slider, собственный компонент): в событии добавьте
  слушатель → этот компонент → `RaiseKey(ActionKey)` и выберите ключ, либо `RaiseDefault()`.
  Так в демо подключён рубильник: `PowerSwitch.onTurnedOn → RaiseKey(switch.on)`.
- **State Flag** — публикует состояние объекта (State Key). Значение меняется из любого UnityEvent вызовом `Set(bool)`;
  в демо `PowerSwitch.onChanged → StateFlag.Set`.

Чтобы связать новый объект со шагом: создайте Action Key, повесьте на объект источник и выберите в нём ключ, затем добавьте тот же ключ в Sequence (или Forbidden) шага.

### Логгер и анализатор

- **Логгеры** — список **Loggers** на объекте `Scenario Runner` в сцене. Можно оставить несколько или ни одного
  (журнал в памяти ведётся всегда). JSON-логгер пишет файлы в
  `%USERPROFILE%\AppData\LocalLow\DefaultCompany\ScenarioConstructor\ScenarioLogs`.
- **Анализаторы** — анализатор по умолчанию задаётся в режиме; список доступных для повторной оценки — поле **Analyzers**
  компонента `Scenario HUD` на объекте `Canvas`. Баллы и штрафы редактируются в ассетах анализаторов.

### Посмотреть журнал и результат

- Во время игры: кнопка **Журнал** слева сверху; после прохождения — экран результата с выбором анализатора.
- Без запуска сцены: **Window → Scenario → Журнал и анализ** — выберите сохранённый журнал (или текущее прохождение в Play Mode)
  и любой анализатор, нажмите «Загрузить и оценить». Кнопка «Папка» открывает каталог с журналами.

`Tools → Scenario → Пересобрать демо-сцену` восстанавливает демо в исходный вид (ваши изменения в демо-ассетах и сцене будут потеряны — спросит подтверждение).

## Техническое описание

### Поток данных

```
 источники (Button/Trigger/Collision/UnityEvent)        State Flag ─► WorldState
        │ ActionBus.Raise(ActionKey)                                  │ (читается условиями шагов)
        ▼                                                             ▼
 ScenarioRunner ──► ScenarioSession ── шаги (IStepLogic) + правила режима (ExecutionRules)
  (сцена)            (чистый C#)    │
                                    ▼ записи LogRecord
                              SessionJournal ──► логгеры (ILogWriter: консоль, JSON Lines, …)
                                    │
                                    ▼ только записи журнала
                              ResultAnalyzer (JournalDigest → AnalysisReport)   ◄── сохранённый .jsonl
```

### Ответственность частей (`Assets/Scenario/Runtime`)

| Часть | Ответственность | Не знает о |
|---|---|---|
| `Actions/` — `ActionKey`, `ActionBus`, источники | Превращают события Unity в действия сценария. | шагах, режимах |
| `State/` — `StateKey`, `WorldState`, `StateFlag` | Логические состояния объектов для контекстных условий. | шагах |
| `Steps/` — `StepDefinition`, `IStepLogic`, `ActionSequenceStep` | Что значит выполнить/нарушить шаг. Ассет неизменяем; состояние прохождения живёт в `IStepLogic`, созданном на сессию. | порядке, режимах, оценке |
| `Definition/` — `ScenarioDefinition`, `ModeProfile`, `StepGroup/Stage`, `ScenarioValidator` | Данные: какие шаги, в каком плане активации, с какими правилами. Проверка конфигурации. | исполнении |
| `Execution/ExecutionRules` (+ `TrainingRules`, `ExamRules`) | Что означает нарушение (повтор / Failed) и когда группа закрывается досрочно. | активации, журнале |
| `Execution/ScenarioSession` | Движок: строит волны активации из плана, раздаёт действия активным шагам, ловит действия вне очереди, применяет правила, пишет журнал. Чистый C#, тестируется без сцены. | Unity-сцене, UI, логгерах, оценке |
| `Execution/ScenarioRunner` | Связка со сценой: шина действий → сессия, журнал → логгеры, перезапуск режима перезагрузкой сцены. | правилах и оценке |
| `Logging/` — `LogRecord`, `RecordTypes`, `LoggerAsset`, `JournalFile` | Контракт журнала и заменяемые выводы. | исполнении |
| `Analysis/` — `ResultAnalyzer`, `JournalDigest`, анализаторы | Оценка **только по записям журнала**. Не бросает исключений: проблемы данных → предупреждения. | сессии и режиме |
| `UI/ScenarioHud` | Отображение: меню, задания, сообщения, результат, журнал. Только читает сессию. | логике |

`Assets/Scenario/Editor` — инспекторы с проверкой и схемой активации, окно журнала. `Assets/Demo` — сцена, ассеты,
демо-компоненты (`PlayerMover`, `PowerSwitch`) и `DemoBuilder`, которым сгенерированы сцена и ассеты.

### Контракт журнала

Каждая запись — `LogRecord { time, type, stepId, result, message, data[] }`, где `data` — список пар ключ/значение.
Типы (`RecordTypes`): `session.start/end`, `step.registered` (план шагов в начале), `group.start/end`, `action`,
`step.activated`, `step.progress`, `step.violation` (флаг `outOfTurn`), `step.retry`, `step.result`
(`Completed | Failed | Skipped`, `attempts`, `violations`). Список открыт: читатели пропускают незнакомые типы и ключи,
`JsonUtility` игнорирует незнакомые поля — новые записи и поля не ломают существующие анализаторы (покрыто тестом).

Анализаторы работают через `JournalDigest` — общий разбор журнала в факты по шагам. Поэтому любой анализатор работает
с журналом любого режима, без кода под конкретные комбинации. Недостающие данные (нет `session.end`, нет списка шагов,
прохождение прервано, неизвестный результат) дают предупреждение в отчёте, а не ошибку.

### Как расширять, не меняя основу

- **Новый тип шага:** класс-наследник `StepDefinition` с `[CreateAssetMenu]`, реализующий `CreateLogic()` →
  `IStepLogic` (`Handle` возвращает `Ignored / Progress / Completed / Violation(причина)`, `IsRelevant` — для правила
  «вне очереди», `Reset` — перед попыткой). Движок, режимы и анализаторы менять не нужно.
- **Новый источник событий:** любой `MonoBehaviour`, вызывающий `ActionBus.Raise(key, gameObject)` (удобно наследовать
  `ActionSource` и вызывать `Emit`). Для готовых UnityEvent код не нужен — `UnityEventActionSource`.
- **Новые правила исполнения (режим):** наследник `ExecutionRules` — `OnViolation` (повтор или Failed),
  `ShouldCloseGroup` (досрочное закрытие группы), `DescribeGroup` (подсказка в HUD). Создать ассет и выбрать его в режиме.
- **Новый логгер:** наследник `LoggerAsset`, возвращающий `ILogWriter` (`Write(LogRecord)` + `Dispose`). Добавить ассет в список логгеров раннера.
- **Новый анализатор:** наследник `ResultAnalyzer` с `Evaluate(records, report)`; обычно начинается с
  `JournalDigest.Build(records, report.Warnings)`. Ассет появится в окне журнала; для экрана результата — добавить в HUD.
- **Новый тип записи журнала:** записать `LogRecord` с новым `type` — существующие анализаторы его пропустят.

### Тесты

`Window → General → Test Runner`:
- **EditMode** (`Assets/Scenario/Tests/Editor`, 17 тестов): смешанная активация из задания, действие вне очереди
  в обеих политиках, повтор в тренировке, порог экзамена, перекрывающиеся группы, последовательность и условие на состояние,
  контрольные 15 и 70 баллов, анализ журнала другого режима, неполный/пустой журнал, JSON с незнакомыми полями.
- **PlayMode** (`Assets/Demo/Tests`, 5 тестов): проходят настоящую демо-сцену — нажимают кнопки пульта, двигают игрока
  и ящик через коллайдеры: экзамен = 70, тренировка 10/5/0 и 105 из 120, режим «по шагам», контекстное нарушение, повтор режима.

## Решения, которые стоит знать

- **Действие вне очереди** засчитывается нарушением шага, только если на действие не отреагировал ни один активный шаг.
  Поэтому одна кнопка может быть запрещённой для активного шага и обычной для будущего, без двойного нарушения.
  В экзамене такое нарушение делает будущий шаг Failed и учитывается в пороге **его** группы
  (если порог набран заранее, группа закрывается сразу при старте).
- **Попытки** считаются по нарушениям: попытка = нарушение или успешное выполнение. Шаг, выполненный после двух нарушений, выполнен с 3-й попытки.
- **Условия на состояние** проверяются в момент каждого действия последовательности. Состояние публикуют объекты сцены через `StateFlag`,
  поэтому ассеты шагов не ссылаются на объекты сцены и переиспользуются свободно.
- **Повторное прохождение** перезагружает сцену: все объекты (ящик, рубильник, игрок) гарантированно возвращаются в исходное состояние.
  Сцена должна быть в Build Settings (демо-сцена там есть).

## Что улучшил бы дальше

Ограничения текущего решения и сознательно не реализованное:

- **Только один тип шага.** `ActionSequenceStep` покрывает простые, последовательные и условные шаги, но нет шагов «по времени»
  (удерживать, уложиться в N секунд), «любое из», счётчиков. Архитектура это допускает (новый `StepDefinition`), но в рамках тестового не сделано.
- **Условия только логические и только «И».** Нет числовых состояний и сравнений, нет условий «ИЛИ». Логичное развитие —
  полиморфный список условий (`[SerializeReference]`) с выбором типа в инспекторе.
- **Политика «вне очереди» и порог задаются на режим/правила целиком.** Переопределение на уровне этапа или группы
  (например, разный порог для разных групп экзамена) — небольшое расширение данных.
- **Редактор плана — стандартный инспектор с вложенными списками.** Удобнее был бы визуальный редактор (колонки этапов, перетаскивание шагов между группами,
  подсветка шагов, не попавших в план). Сейчас есть проверка и текстовая «Схема активации».
- **Много мелких ассетов Action Key.** Это защищает от опечаток, но для больших сценариев нужен поиск/создание ключа прямо из поля шага или источника.
- **Один сценарий на сцену.** `ActionBus` и `WorldState` статические; для нескольких одновременных сценариев их нужно сделать экземплярами, передаваемыми раннером.
- **HUD простой:** legacy uGUI Text, показывает последние 150 записей журнала, нет локализации, нет экспорта отчёта.
  Совместимость анализатора с журналом не фильтруется заранее — вместо этого анализатор выдаёт предупреждения о недостающих данных.
- **История прохождений** хранится только в файлах JSON Lines; сравнение попыток и сводная статистика по нескольким журналам — возможное развитие окна журнала.
- **Демо-сцена генерируется скриптом** (`DemoBuilder`). Это сделано для воспроизводимости; ручные правки демо будут потеряны при пересборке (есть подтверждение).
